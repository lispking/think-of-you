# 设计取舍

这个项目受设备的硬约束挤压得很厉害，几乎每个决定都是被逼出来的。
这份文档记录**为什么是这样**，免得后来者（包括我自己）把代价当成 bug 去"修"。

## 一个按键，怎么撑起几种玩法

Mini 的按键配置里只有一个 `function`，事件只有 `click`；按住超过 3 秒属于系统操作，
**不产生点击事件**。所以应用能拿到的输入只有「短按」，以及短按之间的**时间间隔**。

- 间隔 `< TAP_GAP_MS`（450ms）算同一串手势，停手 `TAP_SETTLE_MS`（700ms）才结算。
- 于是「敲几下」成了词汇：1 想你、2 在忙、3 吃饭了吗、4 晚安、5 开局猜拳、6 发起合奏。

比词汇量更要紧的是**本地立刻有反应**：每敲一下回一声、屏幕上写着敲到第几下、
结算后马上显示"已送出：想你"。原来的版本按下之后本机什么都不做，答案要等对方也按下，
最多等 10 秒——那不是游戏，是寻呼机。

**代价**：手势要等 700ms 静默才发出去；敲得比 450ms 还慢会被拆成两次（这是有意的，
但需要用户理解"慢慢地敲 ≠ 连着敲"）。

## 为什么设备没有「本机身份」

早期版本给每台设备一个不同的 `KEY`，用来滤掉自己的回显。问题是：

- 设备端**没有任何唯一标识**（`app` 只有 `api_version`/`width`/`height`，
  运行环境不开放 `io`/`os`/`package`），身份只能靠烧录时注入，
  于是两台必须各存一份脚本，"同一份源码"这个性质就没了。
- 让设备**自己随机生成**身份也不行：`clock.now()` 只有秒精度，未校时时还返回 `nil`。
  两台同时开机可能拿到同一套随机序列、生成同一个身份，而表现是
  **互相把对方当成自己、两边都不响**——静默失效，比报错难查得多。

现在的做法是认「消息」而不是认「设备」：发送前生成一个随机 token 放进 `Title`，
收到消息时看它是不是自己最近发过的。细节见[协议](protocol.md)。

**推论：角色的区分不能再靠设备。** 合奏需要两个声部，改成靠**会话角色**——
发起方奏主旋律、被叫方奏伴奏，而"谁发起的"双方都能从同一条消息里读出来。

## 为什么合奏的曲子要放慢

`clock.now()` 只到秒。发起方在消息里写下绝对起始秒，两边各自换算成本机时间轴，
于是两边的开场**最多差约一秒**。这是物理下限：测不出来，也修不掉。

- 所以每槽定在 600ms。慢板听上去只是"松"，换成 150ms 的快板，这点误差会直接吃掉半拍。
- **播放基准必须是单调时钟，不能用墙上时间。** 应用每 100ms 对一次表，
  而对表算出的"墙上毫秒"每次都会跳最多 1 秒（锯齿）。开场时换算一次、
  之后只用运行时间推进，节奏才是干净的。

## 心灯为什么用「秒钟的整数部分」

两台要一起脉动，但配对消息的延迟以秒计，靠消息同步做不到。
改用共享的墙上时钟：节拍序号取 `floor(秒 / 2)`，**两台取整的结果完全相同**，
所以相位天然一致，不需要对时。

- 对表频率（`CLOCK_READ_MS`，100ms）决定节拍边界最晚多久被察觉，
  也就是两台灯最多差这么多。
- **代价**：未校时时 `clock.now()` 返回 `nil`，心灯退化成按本机运行时间跳动，两台就不同频了。

## 蜂鸣为什么要一个槽一个槽地推

蜂鸣器队列只有 **4 格**，满了以后新增的音效直接被丢弃，而且**没有任何接口能查询队列状态**。
所以旋律不能一口气塞进去：应用按时间轴推进，到一个槽才推一个音，既不丢也不挤。
休止符（槽值为 0）跳过不发声。

另外，蜂鸣与语音播报会互相抑制（"其他音频活动可能中断或抑制蜂鸣音"），
所以同一时刻只让一个在发声。

## 播报为什么串行且有最小间隔

TTS 同一时刻只允许一个任务，**不排队**：被占用时直接返回 `failed/busy`。
所以应用先等 `on_tts_result` 回来再发下一条，并设 `TTS_COOLDOWN_MS` 的最小间隔。

一批消息只念一条是天然的：整批消息在同一个回调里同步处理，`uptime_ms` 不变，
第二次播报必然落在最小间隔内而被拒。

## 启动阶段为什么禁止播报

运行器禁止在源码、`on_start()`、启动的第一次 tick 里调用 `tts.speak`。
协议上不会在这时投递对端消息，但应用还是加了一道 `booted` 保险，
防止边界情况把应用直接抛死（参数非法会产生 Lua 异常，而 `pcall` 不可用）。

## 存档为什么要节流

- 平台限定同一存档槽写入至少间隔 10 秒，应用合并到约 11 秒写一次，避免 `rate_limited`。
- 存档上限 32 项 / 1024 字节，值为有限的数字、布尔或 ≤256 字节字符串，**不支持嵌套**。
- 比分结算这类"丢了就心疼"的时刻会强制写一次（`persist(true)`）。
- **长势按墙上时间回落**，所以关机多久也算数；如果按运行时间算，一重启就会"复活"。

## 为什么三个玩法都塞进同一个应用

设备一次只能装一个应用——上传即替换当前应用。所以不能做成三个独立小应用。
解决办法是让**同一个按键的手势**分流：1-4 传话，5 开局猜拳，6 发起合奏；
对局进行中 1-3 又变成"出招"。

**代价**：手势的含义依赖上下文，屏幕上必须随时说清当前处于哪种状态。
