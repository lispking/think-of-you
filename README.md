# 想你机 · Think of You

两台 LingClaw，一个按键，**几种心情**。

按键只有一个，但「敲几下」已经够用：一下想你、两下在忙、三下吃饭了吗、四下晚安，
五下开一局猜拳，六下两台一起奏一段。送出时自己这台立刻回你几声、屏幕上直接显示
送出的是哪句；对方那台在下次轮询里用它自己的声音念出来，并把你的节奏原样敲回去。

除了消息，还有两样不靠网络的东西。**同频心跳**：两台用同一个墙上时钟算节拍，
指示灯一起脉动，两个房间一起呼吸。**想念会长大**：交换累积长成一株像素植物，
放着不管会蔫，攒够了开花。

没有文字输入，没有未读红点，没有「对方正在输入」。

## 玩法

| 敲 `function` 键 | 送出的 | 对方那台 |
| --- | --- | --- |
| 1 下 | 「有人在想你。」 | 敲 1 声把你的节奏敲回来，再念出来 |
| 2 下 | 「在忙，等下回你。」 | 敲 2 声 + 念出来 |
| 3 下 | 「吃饭了吗？」 | 敲 3 声 + 念出来 |
| 4 下 | 「晚安，好好睡。」 | 敲 4 声 + 念出来 |
| 5 下 | 发起一局猜拳 | 两边各敲 1/2/3 出石头/剪刀/布，各自算出同一个结果 |
| 6 下 | 发起合奏 | 两台从同一秒开始，一台奏主旋律、一台奏伴奏 |

- 敲多少下靠**间隔**分辨：相邻两下间隔小于 `TAP_GAP_MS`（默认 450ms）算同一串，
  停手 `TAP_SETTLE_MS`（默认 700ms）才结算。慢慢地敲 ≠ 连着敲。
- 对局进行中，1/2/3 下变成「出招」，不再是传话。
- 连点会被冷却拦住（显示「别急，慢一点」）；发送失败显示「没送出去」，计数也不虚增。
- 送出次数、收到次数、轮询游标、长势、连续天数、比分都会存档，重启后接着用。

## 它是怎么工作的

### 两台怎么说话

设备只能**主动轮询**，没法被动接收推送，所以两台需要一个公共中转。
两台跑**完全相同的脚本**，不需要区分身份：自己的回显靠每条消息自带的随机 token 认出来。
这里用 [ntfy.sh](https://ntfy.sh)（免费、免注册、支持 HTTP 轮询）：

```
设备 A 敲完 → POST https://ntfy.sh/<TOPIC>          （Title 头 = 本条消息的随机 token）
设备 B 轮询  → GET  https://ntfy.sh/<TOPIC>/json?poll=1&since=<上次时间戳>
            → 解析出消息 → Title 不在自己刚发过的 token 里 → 响铃 + 播报
```

消息体是「类型\|参数」的短文本，没有前缀的一律当普通文本念，
所以对面就算还跑着旧版脚本也依然能说话：

| 消息体 | 含义 |
| --- | --- |
| `w\|<n>` | 敲了 n 下的短语 |
| `m\|<曲>\|<起始秒>` | 合奏，双方在同一个绝对秒开始 |
| `r\|<动作>` | 猜拳：0 表示想开局，1 石头、2 剪刀、3 布 |

`since` 用上次**已处理消息的时间戳 +1**，所以重启或断网后也不会重复播报；
必要时用 `since=1m` 从一分钟前开始拉取。两条消息用消息 `id` 去重。
闲着时 10 秒轮询一次；对局或合奏一开始就切到 2 秒，结束再退回去。

### 同时做一件事，不必互相等

轮询延迟以秒计，所以「两台同时」不能靠消息对齐。它们各自读自己的墙上时钟：
心灯取**秒钟的整数部分**定位节拍，两台取整结果完全相同，相位自然一致；
合奏则由发起方在消息里写下一个绝对起始秒，两边各自换算成本机的时间轴。

代价是精度：`clock.now()` 只有秒，两台的开场最多差约一秒。所以曲子刻意放慢
（每槽 600ms），听上去只是「松」，不会散。

### 想念会长大

长势按**墙上时间**回落，所以关机多久也算数；每次送出 +8、收到 +14，到 90 开花。
连续天数按本机日期算：昨天也有来往就 +1，断了就重头算。

## 快速开始（模拟器，零配置）

```sh
# 打开模拟器，选择本项目根目录下的：
think-of-you.lua
```

点击预览画面后连着按空格键（Mini 预设的 `function` 映射）就是敲击：
敲一下停手是「想你」，敲三下停手是「吃饭了吗」。
模拟器使用电脑真实网络，`on_http_response` 走的是真 ntfy 请求。
底栏「播报」侧栏可以查看并确认「对方」传来的播报文本。

## 配对两台设备

1. **换掉主题名。** ntfy 的主题名就是密码，公开主题任何人都能订阅，
   所以要用一段难猜的字符串。**两台填成同一个**，并且跑**同一份脚本**。
2. 一条命令烧两台。脚本会注入 `TOPIC`、按 `transport_id` 找到每台设备、
   烧完再回读校验：

   ```sh
   ./flash.sh --topic lingclaw-think-换成随机串
   ```

   之后重烧（比如设备重启后，脚本源码只存在内存里）直接 `./flash.sh` 即可，
   主题名会记在 `device-flash.topic`，不进版本库。
3. 手工烧录也行，两台烧**同一份**：

   ```sh
   adb push think-of-you.lua /miniapp/think-of-you.lua
   ```

   上传后设备立即运行。两台设备屏幕底部「主题 …xxxx」一致即为同题。
4. 想改回设备上正在跑的版本：

   ```sh
   adb pull /miniapp/miniapp.lua ./device-app.lua
   ```

## 配置

脚本顶部集中了所有可调项：

| 变量 | 含义 | 默认 |
| --- | --- | --- |
| `TOPIC` | ntfy 主题，**两台必须相同**，务必改掉 | `lingclaw-think-CHANGE-ME-8f3a` |
| `WORDS` | 敲 1-4 下送出的短语（`say` 是对端念的，`hint` 是本机标签） | 4 句中文 |
| `POLL_MS` / `POLL_BUSY_MS` | 空闲 / 对局期间的轮询间隔 | `10000` / `2000` |
| `SEND_COOLDOWN_MS` | 两次发送之间的最小间隔 | `1200` |
| `TTS_COOLDOWN_MS` | 两次播报之间的最小间隔 | `2000` |
| `TAP_GAP_MS` / `TAP_SETTLE_MS` | 同一串手势的最大间隔 / 结算前的静默 | `450` / `700` |
| `BEAT_MS` | 心灯节拍长度 | `2000` |
| `GROW_DECAY_SEC` / `GROW_FEED_SENT` / `GROW_FEED_GOT` / `GROW_BLOOM` | 长势回落速度 / 送出喂多少 / 收到喂多少 / 开花线 | `1800` / `8` / `14` / `90` |
| `STEP_MS` / `SONG_LEAD_SEC` | 合奏每槽时长 / 开场前留的传播时间 | `600` / `15` |
| `MATCH_TIMEOUT_MS` | 一局猜拳最多等多久 | `60000` |

## 设计取舍

- **为什么用轮询而不是推送？** 设备没有长连接/被动接收能力，
  HTTP 也没有 WebSocket，只有 `http.request`。轮询是唯一可行的收信方式。
- **为什么只有一个键还够用？** 敲击的**间隔**是天然的第二维信号：相邻两下小于
  `TAP_GAP_MS` 才算同一串，停手 `TAP_SETTLE_MS` 才结算，于是「敲几下」成了词汇。
  更关键的是本地立刻能给反馈（每敲一下回一声、屏幕上写着敲到第几下），
  不必等对端回话——这正是原来最缺的东西。
- **合奏的声部凭什么分得开？** 不能靠设备身份，那正是已经删掉的东西。
  改成靠**会话角色**：发起方奏主旋律、被叫方奏伴奏，而「谁发起的」双方都能从
  同一条消息里读出来。两台依旧跑完全相同的源码。
- **为什么曲子要放慢？** 墙上时钟只有秒精度，两台各自换算出的开场最多差约一秒。
  600ms 一槽的慢板听上去只是「松」；换成 150ms 的快板，这点误差会直接吃掉半拍。
- **为什么蜂鸣要一个槽一个槽地推？** 蜂鸣器队列只有 4 格、满了就丢弃，
  而且没法查询队列状态。所以按时间轴推：到一个槽才推一个，既不丢也不挤。
- **为什么对局时要自适应加密轮询？** 回合制要跟得上手，但全天每 2 秒拉一次会白白
  骚扰公共实例。所以只在有对局或合奏时加密，并且一开始就把下一次轮询提前，
  不等满一个空闲周期。
- **为什么不需要 `KEY`？** ntfy 主题里所有人都看得到全部消息，包括自己发的那条，
  所以必须认出并滤掉自己的回显。早期版本给每台设备一个不同的 `KEY`，
  但设备端**没有任何设备唯一标识**（`app` 只有 `api_version`/`width`/`height`，
  运行环境不开放 `io`/`os`），「我是谁」只能靠烧录时注入，两台就必须各存一份脚本。
  现在改成：发送前生成一个随机 token 放进 `Title` 头（`Title` 不显示在界面上），
  收到消息时看这个 token 是不是自己刚发过的——认「消息」而不是认「设备」，
  于是两台可以跑**完全相同的源码**。
  这也顺带避开了「让设备自己随机生成身份」的坑：`clock.now()` 只有秒精度，
  未校时时还返回 `nil`，两台同时首次开机可能拿到同一套随机序列、生成同一个身份，
  而表现是互相把对方当成自己、两边都不响，属于**静默失效**。
- **为什么播报要节流、串行？** TTS 同一时刻只允许一个任务且**不排队**，
  被占用时直接返回 `failed/busy`。所以先等 `on_tts_result` 回来再发下一条，
  并设最小间隔。
- **为什么有一道 `booted` 保险？** 运行器禁止在启动阶段（源码、`on_start`、
  第一次 `on_tick`）调用 `tts.speak`。协议上不会在这时投递对端消息，
  但这道保险能防止边界情况下把应用直接抛死。
- **为什么存档要节流？** 平台限定同一存档槽写入至少间隔 10 秒，
  这里合并到约 11 秒写一次，避免 `rate_limited`。

## 已知限制与注意

- **公共主题没有隐私。** 消息内容对任何知道主题名的人可见。
  主题名要足够随机，别用生日、昵称这类可猜字符串。
- 想彻底私有化，可以自建 [ntfy 服务端](https://docs.ntfy.sh/install/)，
  或在 POST/GET 上加 `Authorization` 头（脚本的 `headers` 已支持）。
- ntfy.sh 公共实例有速率限制；`POLL_MS` 不建议低于 5 秒。
- 依赖 API 4（`http` / `json` / `tts`），需要设备有网络、扬声器和指示灯能力
  （Mini 固件 3.0.2 及以上满足）。
- **心灯与合奏要求设备已校时。** `clock.now()` 未校时时返回 `nil`：心灯会退化成
  自己的节奏（两台就不同频了），合奏会拒绝发起并提示「没校时，先连上网」。
- **麦克风用不上。** Mini 的硬件能力里 `microphone` 是 true，固件也有唤醒和录音命令，
  但 Lua 侧只开放了 `app` / `input` / `screen` / `led` / `buzzer` / `clock` /
  `storage` / `http` / `json` / `tts`，没有任何音频输入接口，
  所以「录一句给对方听」这类玩法现在做不到。
- **画面只有矩形和文字。** 没有图像接口，那株植物是一块块矩形拼出来的；
  指示灯也只有一色，只能亮、灭、闪。
- **源码只存在设备内存里。** 上传的应用不会留在闪存，设备重启后要重新烧录
  （`./flash.sh`）；`storage` 存的东西会保留。
- **同一批设备的 ADB 序列号可能相同。** 两台一起插上时 `adb -s <序列号>` 会歧义，
  要用 `adb -t <transport_id>` 区分；`flash.sh` 已经自动处理。
- 响应体默认上限 8KB，脚本放宽到 12KB；主题闲置一周以上会清空历史，
  首次可用 `since=1m` 兜底。
